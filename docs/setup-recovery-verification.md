# Setup interruption and recovery verification

Run the installer regression coverage with:

```sh
bun test electron/runtime/installerRecovery.test.ts
```

The tests use the real `RuntimeInstaller`, its real `spawn` command runner, process cancellation, on-disk generation directories, dependency report writes and activation/rollback records. `fixtures/setupPython.ts` supplies an executable Bun-backed command that **simulates Python, pip and package/readiness outputs**. No Python packages, models, CUDA runtime or MLX backend are installed or imported. These are actual child-process/filesystem integration tests with synthetic command behavior, not native inference or real network-download evidence.

Each temporary profile starts with an existing active runtime, previous executable fixture interpreter and dependency-report bytes, a separate opposite runtime, and fixture settings/history. Nonzero child exits at interpreter discovery, environment creation, installer preparation, runtime packages, package compatibility, readiness, freeze and inventory are exercised for both speech and optional Magic. Windows CUDA stage failures are also simulated. Successful child exits followed by real filesystem failures writing freeze or inventory reports are covered separately. Every failure preserves the original pointer, interpreter, reports, opposite runtime, settings and history, publishes no installed-success event, and permits an explicit retry on the same installer into a fresh generation. A fresh installer reader can still run the previous executable's readiness command while the failure controls remain set.

Interruption cases exercise installer/runtime/CUDA downloads plus freeze and inventory probes without stage-output callbacks. The command writes partial bytes into its candidate and continues appending while alive. Tests observe the real child PID and growing partial file before calling `stop()`, await failure within a bounded time, verify that the child exited, and retain the inactive partial candidate. Explicit retry completes into a different generation, records freeze and inventory reports, and only then publishes installation success. The synthetic metadata report identifies its interpreter as `SyntheticFixture`; it is not a fabricated hardware inventory.

Linux, Apple Silicon MLX and Windows backend selections are simulations on the test host. The executable shim uses POSIX shebangs, so these process tests are skipped on native Windows. Windows process termination and real Mac/Windows package/backend readiness still need their native runners. Fixture bytes stand in for interrupted downloads; no network, owner runtime, personal transcript or model cache is touched.

The service coverage runs `bun test electron/services/setupRecovery.test.ts` in isolated Bun child processes. It uses the actual `AsrService`, installer command runner and generation activation/rollback; only Electron's application context and model-worker responses are mocked. Both speech and Magic cases check failed model download/warmup against fresh, legacy and generated runtime layouts, preservation of the other runtime and existing cache/profile bytes, and a successful explicit retry using a different candidate. Duplicate setup requests share one installation and stay Loading until the model response completes. Shutdown during that response stops the worker, rolls back and permits an explicit new setup.

Restoring the other requested preloaded model is also part of setup. Previously, if the primary candidate loaded successfully and that final restoration failed, setup rejected but left the candidate active while reporting that the existing runtime was preserved. The service now includes that final await in its existing stop-and-rollback boundary. Two regressions fail the prior-runtime pointer assertion on the original code and pass with the complete boundary; retry validates both requested models. A failed setup never edits the opposite runtime's activation record or the prior generation's interpreter/report files. These are mocked model failure paths, not interrupted real checkpoint downloads or native warmup evidence.

Additional POSIX permission fixtures reject the final activation write after dependency reports complete; the prior pointer and runtime remain usable and an explicit retry succeeds once permissions are restored. Separate service fixtures reject rollback writes after model loading fails. An unwritable activation record cannot be restored: the service retains both failure causes, stays in Error, and explicitly reports incomplete restoration rather than advertising a preserved active runtime. The old generation's interpreter/report and existing profile/cache bytes remain intact. Repair can be retried after resolving the filesystem error. Permission-denial cases are skipped for privileged root processes and native Windows.

The synthetic child cooperates with SIGTERM and creates no descendants. These checks do not establish cleanup of stubborn pip/build subprocess trees, physical network interruptions, power-loss durability, or native Windows process termination.
