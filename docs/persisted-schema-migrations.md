# Persisted schema versions and reversible migrations

Settings use `schemaVersion: 1` separately from `workflowVersion: 1`, which records rewriting opt-in migration behavior. History stays a JSON array; each transcript has `schemaVersion: 1`. Vocabulary rules stored in settings, exported rule bundles and personal profiles each have `schemaVersion: 1`. The existing personal-profile collection and profile-entry versions remain 1.

Absent schema versions identify supported legacy data. Writes add explicit current versions. Future, null, string, zero and malformed settings/transcript/rule versions are rejected before normalization or publication. Both settings and all history entries are checked before startup migration writes. Rules are checked before settings writes and imports; a future rule cannot be silently normalized to the current format. The existing future-profile contract is preserved: opaque newer profile documents remain stored read-only; edits/downgrades are rejected and no profile is activated.

`src/persistedSchema.ts` supplies additive version stamping and reversible in-memory migration snapshots. `reversePersistedSchema` returns the exact original JSON-shaped value, including unknown metadata and whether the version was absent. This reversal requires its original snapshot; merely deleting a version marker is not a general rollback strategy.

Startup normalization preserves literal raw, edited, personalized and rewritten transcript strings rather than trimming or truncating them. Unknown transcript metadata/provenance fields survive legacy migration. Already versioned transcripts are cloned intact. Invalid transcript text now blocks migration instead of silently dropping a record. Startup does not truncate historical arrays to the insertion retention limit; ordinary new-record retention still caps history at 500. Invalid/oversized vocabulary collections and oversized literal text blocks similarly block migration instead of silently deleting/truncating data.

Existing SHA-256-verified raw `migration-backups` snapshots complete before migration publishes settings/history, so those whole-file snapshots preserve the original source bytes as well as legacy fields changed by prior workflow normalization. Atomic per-file temporary-write/rename remains in use. Settings and history are independent documents; a failed second publication may leave one upgraded document, which the supported legacy/current readers can reopen. Keep the raw backup for restoring the earlier pair. Explicit history deletion continues to revoke history from migration backups.

Fixtures live at `tests/fixtures/schema-migrations/legacy-roundtrip.json`. The adjacent `roundtrip.ts` exports executable assertions for additive migration, exact snapshot reversal, repeated migration, future-schema rejection and opaque profile preservation. Fixtures include whitespace-sensitive layers, historical model identity, requested/recognized language and unknown provenance metadata. They are intentionally unrun in this implementation pass.

## Integration boundaries

The durable audio-import job store is implemented separately by [issue #199](https://github.com/JEMostert/delulu-talks/issues/199), published in [PR #449](https://github.com/JEMostert/delulu-talks/pull/449). Its `electron/services/audioJobs.ts` contract stores `import-jobs.json` as `{ schemaVersion: 1, jobs: [...] }`, requires exactly version 1 on read, preserves the file when an unsupported version or invalid metadata is encountered, and publishes writes by temporary-file rename. It has no older persisted job format to migrate. This branch does not duplicate that store; integration depends on #199. Future job schema changes need real prior/current reversible fixtures and backup/restore support. Personal profiles already have a versioned contract and are not automatically activated. Version markers do not establish native behavior or verified migrations.
