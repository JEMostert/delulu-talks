# Backend capability negotiation

Before loading speech or writing, the desktop sends a versioned `capabilities` command for that engine to the same persistent worker. Python answers from its implemented adapter contract without importing model/GPU libraries or downloading weights. The desktop validates schema version, engine/model family, backend identity, feature booleans and the bounded unique language list. The Details disclosure on each model card displays the negotiated report; stopped/failed workers clear it and a new load negotiates again.

Current buffered R2T2 adapters accept the explicit language hints already mapped by the application. The CUDA Transformers adapter also accepts `auto`, which leaves language detection to R2T2, and reports vocabulary biasing: transcription may carry `hotwords`, a comma-separated list (at most 150 words and 3,000 characters) of enabled vocabulary-correction spellings, own words before word-pack words, that R2T2 receives as its context prompt. The MLX adapter reports neither until it is validated on a Mac. The CPU adapters (backend `onnx-cpu`) report no vocabulary biasing: Canary 180M (`canary`) accepts `en`, `de`, `fr` and `es`; Parakeet v2 (`parakeet`) accepts `en`; Parakeet v3 advertises no language hints and detects the language itself. All adapters report timestamps unsupported. Optional writing reports these speech controls unsupported. A request cannot silently turn on an unsupported control; invalid/unsupported fields reject before dispatch. Transcription checks its requested hint against the negotiated list before inference.

Capabilities describe accepted software controls, not hardware availability, model accuracy, calibrated timestamps or native platform validation. The backend name identifies the selected adapter and does not assert that its GPU/runtime has passed an owner-machine test.
