# Worker protocol version 1

Every JSON-lines request and terminal response carries `protocolVersion: 1`. Request IDs are nonempty strings of at most 128 UTF-8 bytes, commands at most 64 bytes. The desktop generates UUIDs and validates before spawn/write; Python independently validates before dispatch. Missing or incompatible versions produce an actionable restart/repair error rather than accepting a different wire contract. Python returns a correlated request-local rejection for a valid ID; a malformed ID cannot be correlated and terminates the desktop generation. Structured progress lines retain their separate `@delulu-progress:` prefix and carry the active request ID, command, stage and bounded detail.

Request fields use their actual types without string/boolean coercion. Load commands accept an optional string cache path; Magic load accepts only the three existing Qwen 3.5 catalog IDs. Transcription requires a nonempty audio path, an optional string language hint, and finite nonnegative duration. Rewriting requires string text and optional existing preset (`polish`, `concise`, `structured`, `prompt`), string instructions and boolean inference permission. Transport text/instructions caps are 500,000/4,000 UTF-16 units; the existing 50,000-character writing backend limit still applies. Python recognizes the existing ten worker commands; unknown commands receive a correlated rejection.

Success responses contain a result and no error; failures contain a nonempty error of at most 8,000 UTF-8 bytes and no result. Python validates backend results before emitting, and the desktop validates both the envelope and the matching pending command result before completing it. Status results require a boolean loaded flag; transcription requires text/language and finite nonnegative duration/processing time; rewriting requires text/model, processing time, input/output character counts and inference-permission metadata. Shutdown acknowledges `shutdown: true`. Nullable status model/device values and optional inference timing remain supported. JSON rejects nonfinite numbers and more than 64 nesting levels.

The byte, queue and diagnostic limits in [worker bounds](worker-bounds.md) remain in force. Version/schema errors preserve source audio, model runtimes, settings and transcripts. This is a wire contract, not evidence of native MLX/CUDA behavior or acoustic streaming. The opt-in runtime smoke uses the same versioned subprocess entrypoint and production schema instead of bypassing it with direct dispatch; it still requires existing models and explicit native invocation.

## Progress events

A progress line contains `{protocolVersion: 1, type: "progress", id, command, stage, detail}` and an optional finite `fraction` between zero and one. IDs match terminal response IDs; stages/commands are nonempty strings bounded to64UTF-8bytes, and detail is at most4,000UTF-8bytes. The desktop validates the event separately from terminal responses, then publishes it only while the matching ID and command are pending. Unknown IDs, completed work, mismatched commands and prior generations cannot update the current status. Malformed reserved-prefix events fail the generation with intentional repair/retry; ordinary library logs are never interpreted as progress.

Python scopes the operation ID/command around dispatch with a context variable that resets on exit. MLX and Windows R2T2 download/conversion/loading emitters use that context; a direct backend call without a worker operation logs to stderr instead of inventing an ID. Existing UI callbacks retain bounded text compatibility and can also receive structured metadata. The optional native smoke consumes the same schema. Events do not invent model percentages or expose transcript contents.

This progress integration is UNVERIFIED. No tests, build, typecheck, formatting, packaging or native inference ran per user instruction; fixture wire migrations are source-only.
Audio streaming has a separately specified [chunk/session contract](audio-stream-protocol.md). Its reserved commands remain rejected until an incremental-audio backend and transport adapter are implemented.
